## Field definitions

- **full**: the CLI can complete provisioning + config + verification end-to-end; the deploy skill can close the loop fully automatically.
- **partial**: the CLI can only complete part of the main flow; the deploy skill must hand the partial segment to the user in the console (output a deep link + screenshot instructions + wait for the user to reply "ok" before continuing).
- **false**: the CLI cannot provision the product at all; the deploy skill immediately takes the fallback_route and does not enter the Phase 0 automation branch.

## Binding with the SKU yaml

Every product code appearing in a `references/sku-params/*.yaml` products list must be findable in this matrix. If any product hits partial/false, it is **ANNOUNCED at Phase -1.5, not turned into a stop-and-wait gate**. The console-only / self-purchase add-ons (Token Plan, PDS, the OSS package) are NOT preconditions for the CLI-reachable resources, so a manual item must never suspend or decline the deployment here:

- partial → record the step in `state.manual_steps` and NAME it in the reachability summary, then **keep going and provision everything CLI-reachable**. Do NOT enter a "waiting for the user to finish in the console" suspended state at -1.5. The one real blocking point is the later step that actually depends on it (e.g. the OSS bucket needs its package first → that check lives at the bucket step in `provision.md`), never here.
- false (console-only, e.g. Token Plan) → NAME it as a step the user opens themselves later and hand out its `fallback_route` for reference. Do NOT decline the order over an optional self-purchase add-on — the CLI-reachable resources are still created. Tell the user something like:

```text
这个套餐里的 ${product} 目前没法用命令行一键开，需要你自己在控制台点几下：${fallback_route}。这个等会儿到那一步我再提醒你，现在我先把能自动开的都准备好。
```
